# RQ-0036 - A CPU-agnostic probe template: the core's startup, fault handling, linker script and toolchain come from the project, not the scaffold

Every hardware-twin project receives the same probe template from
`writeProbeTemplate` (`packages/agent-factory/src/scaffold.ts`), whichever
simulator it uses. The template was lifted from aselsan-bfi, whose board is a
SmartFusion2 with a Cortex-M3, and the Cortex-M3 stayed in it as a hidden
assumption:

- `probes/_template/main.c` carries an `.isr_vector` table of sixteen Cortex-M
  exception slots and a `reset_handler` that is that table's second entry.
- `probes/_template/probe.c`, the runtime the README says not to edit, reads
  CFSR and BFAR at `0xE000ED28`/`0xE000ED38` in `probe_fault_report`, skips
  the faulting instruction by Thumb-2 encoding rules, and `probe_fault_handler`
  is a naked `mrs r0, msp` stub.
- `probes/_template/linker.ld` lays out a 64K flash at 0 and 16K RAM at
  `0x20000000` and keeps `.isr_vector` first.
- `templates/renode/scripts/build-probe.mjs` passes `-mcpu=cortex-m3 -mthumb`
  and runs `arm-none-eabi-gcc`; `templates/simics/scripts/windows/Build-Probe.ps1`
  does the same with `arm-none-eabi-*.exe`.
- `templates/renode/ci/Dockerfile` installs the `arm-none-eabi` Arm GNU
  toolchain and the CI image tag in `.gitlab-ci.yml` names it (`armgnu-15.2.rel1`).
- `platforms/board.repl` and `scripts/run-probe.resc` give Cortex-M/NVIC as
  their example, and `probes/README.md` and `AGENTS.md` do not say the core
  is a choice at all.

On 12 October `factory new ecu-csw-twin --simulator renode` produced this
template for a board whose processor is an NXP LS1023A, a 64-bit Cortex-A53.
Nothing refused: the project looked ready, and its first probe would have
compiled for the wrong architecture with the wrong toolchain, or not at all
once `#error` in `board.c` was removed. The core of a board is a fact the
scaffold cannot know, in the same way the console UART is one, and the
template already treats the UART honestly: `board.c` is an `#error`
placeholder the first requirement fills from the board. This requirement does
the same for the core.

## What it does

**The runtime is split along the CPU line.** `probe.c` and `probe.h` keep
everything that is the trace contract and the same on every core: the step
list, the read-before-console order, the line printers, the WAIT spin and the
MEM pattern test with its `fault_pending`/`fault_address` protocol. The two
places where it touched the core move out behind a small interface declared
in `probe.h`:

- `probe_fault_report` becomes what the CPU file calls from its exception
  handler with the faulting address and a way to resume; the runtime decides
  whether a MEM step was in progress and what to print. The Cortex-M register
  reads and the Thumb-2 skip leave `probe.c`.
- The `wfi`/`dsb` instructions in the runtime become `probe_cpu_idle()` and
  `probe_cpu_barrier()`, supplied by the CPU file.

**A new template file, `probes/_template/cpu.c`, holds what depends on the
core**: the exception vectors or vector table, the entry point that sets up
the stack and the C runtime (`.data` copy, `.bss` clear) and calls
`probe_run()`, the fault handler that reaches `probe_fault_report`, and the two
hooks above. The scaffold writes it the way it writes `board.c` today: a
commented statement of what each piece must do and an `#error "Write the
startup, vectors and fault handler for this board's core, then delete this
line."`. `main.c` is left with the step list only. `linker.ld` keeps its
section layout, but its `MEMORY` block is unfilled and an `ASSERT(0, ...)`
naming the file stops the link until the origins, lengths and entry are the
board's, rather than linking at an address the board does not have.

**The toolchain is a project file, `probes/toolchain.json`**, committed
beside the probes, since which compiler and flags built the committed ELFs is
a property of the project and not of the machine:

```json
{
  "prefix": "arm-none-eabi-",
  "cflags": ["-mcpu=cortex-m3", "-mthumb"],
  "ldflags": [],
  "ci": { "armGnuTarget": "arm-none-eabi" }
}
```

`prefix` is prepended to `gcc`, `objcopy` and `size`; `cflags` and `ldflags`
are placed before the flags the build scripts own (`-Os -ffreestanding
-fno-builtin -fdata-sections -ffunction-sections -Wall -Wextra -Werror
-nostdlib`, `--gc-sections`, `--build-id=none`, the source-hash define), which
stay in the scripts because the probe contract depends on them.
`SIMULATOR_TOOLCHAIN_BIN` keeps its meaning: where that toolchain's `bin` is
on the machine that builds. The scaffold writes the file with `prefix` and
`cflags` empty and `ci.armGnuTarget` empty. `build-probe.mjs` and
`Build-Probe.ps1` read it and refuse, before any compiler runs, when the file
is missing or `prefix` is empty, saying which file to fill and that
`probes/README.md` names the examples. `Run-Probe.ps1` resolves `objcopy`
through the same prefix. The probe source hash includes `toolchain.json` so a
flag change invalidates the committed trace the way a source change does.

**CI follows the file.** The renode Dockerfile takes the Arm GNU target
triple as a build argument (`ARM_GNU_TARGET`), and `ci/build-image.sh` and
the `build_ci_image` job read `ci.armGnuTarget` from `probes/toolchain.json`
and pass it. The image tag stays per project (one project, one core); the
README says to rebuild the image when the target changes. The known tarball
digests for `arm-none-eabi` and `aarch64-none-elf` of the pinned release are
in the Dockerfile, and a target without a digest fails the build with a
message rather than skipping the check. The image check runs
`<target>-gcc --version`.

**The Cortex-M3 pieces become an example, not the default.** The present
`cpu.c` content (vectors, `reset_handler`, fault handler with CFSR/BFAR and
the Thumb-2 skip), `linker.ld` with the SmartFusion2 eNVM/eSRAM layout, and
`toolchain.json` move to `packages/agent-factory/templates/probe-cpu/cortex-m3/`
with a README that says which board they were verified on. `probes/README.md`
in a generated project names that directory and says: copy the one for your
core, or write it from the core's reference manual; a core with no example
yet is the first requirement's job. The scaffold's `board.repl` and
`run-probe.resc` comments show the shape without naming a core, and the
generated `AGENTS.md` says in one line that the core, its startup and its
toolchain are the project's facts, recorded in `probes/_template/cpu.c`,
`linker.ld` and `probes/toolchain.json`, and that a probe template still
carrying the placeholder means the project has not chosen them.

**Existing projects are not touched.** aselsan-bfi, bfi-simulator and twin3
carry their own copies of the template, verified on hardware; nothing in
this requirement rewrites a generated project. A project that upgrades does
so by copying the new `probe.c`/`probe.h` and the cortex-m3 example, which
together are what it has today.

## Acceptance Criteria

- `factory new x --simulator renode` and `factory new x --simulator simics`
  both write `probes/_template/cpu.c` with the `#error` placeholder,
  `probes/_template/main.c` without a vector table or `reset_handler`,
  `probes/_template/linker.ld` with the `ASSERT` that stops an unfilled
  link, and `probes/toolchain.json` with empty `prefix`, `cflags`, `ldflags`
  and `ci.armGnuTarget`; neither `probes/_template/probe.c` nor `probe.h`
  contains `0xE000`, `cortex`, `thumb`, `msp` or `wfi`.
- No file written by either scaffold names a core as the default:
  `cortex-m3` appears only in `probes/README.md` (the example) and
  `ci/Dockerfile` (a digest), and `arm-none-eabi` or `-mthumb` elsewhere only
  on a line that lists it as one choice beside `aarch64-none-elf`.
- In a generated renode project with `toolchain.json` as scaffolded,
  `factory probe build RQ-0001` stops before running any compiler and its
  message names `probes/toolchain.json` and `probes/README.md`; the same for a
  simics project through `Build-Probe.ps1`.
- With `probes/toolchain.json`, `cpu.c` and `linker.ld` copied from
  `templates/probe-cpu/cortex-m3/` into a generated renode project, and
  `board.c` filled for a SmartFusion2 MMUART, `factory probe build` produces
  an ELF whose `PROBE_SOURCE=` matches the source hash, and that hash changes
  when `toolchain.json` changes.
- The cortex-m3 example copied into a generated renode project, with a stub
  `board.c`, builds through `build-probe.mjs` with the arm-none-eabi
  toolchain into an ELF that embeds the source marker, with `-Werror` on:
  in the aifactory test when the toolchain is on PATH (skipped with a message
  otherwise), and on the lab host through the remote path. With the
  scaffolded `linker.ld` in place of the example's, the same build stops at
  the `ASSERT`; with the scaffolded `cpu.c`, at the `#error`.
- The generated renode Dockerfile selects the tarball and its digest from
  `ARM_GNU_TARGET` for `aarch64-none-elf` and for `arm-none-eabi`, refuses
  any other target, and `ci/build-image.sh` and `build_ci_image` pass the
  target read from `probes/toolchain.json`.
- `probes/README.md`, the generated `AGENTS.md`, `platforms/board.repl` and
  `scripts/run-probe.resc` say the core is the project's choice and where it
  is recorded, and name no core as a default.
- Every existing scaffold test passes with the template change, and
  `pnpm test` is green.
